# プロジェクト設定

rsfiler は、xyzzy のファイラを参考にした、キーボード操作優先の 2 ペイン ファイラ。Tauri v2 (バックエンド: Rust、フロントエンド: React 19 / TypeScript / Vite) で作る。

## コマンド

すべてリポジトリのルートで実行する (`package.json` の scripts)。

## 開発ワークフロー

- **開発サーバーを起動**: `npm run tauri:dev` — フロントエンドと Rust は両方とも変更時に自動リロード
- **テスト**: `npm run test`（`src/` に対する Vitest）と `cargo test`（`src-tauri/` に対する）
- **フォーマット + リント**: `npm run check`（format:check、lint、test を実行 — CI ゲート）
- CI は `main` へのすべてのプッシュ/PR で同じ内容を実行し、別のジョブでカバレッジ (`npm run coverage`。フロントエンドもバックエンドも 100% でなければ失敗する) も実行する

## プロジェクト構成

- `src/`: フロントエンド (React / TypeScript)。
- `tests/`: フロントエンドのテスト。`src/` と同じ構成で置く (`src/features/explorer/view.ts` のテストは `tests/features/explorer/view.test.ts`。`setup.ts` は vitest の setupFiles)。
- `src-tauri/`: バックエンド (Rust)。
  - `src/lib.rs`: Tauri の初期化 (`run`) と IPC コマンドの登録 (`specta_builder`)。
  - `src/commands/`: フロントエンドから呼ぶ IPC コマンド (`#[tauri::command]`)。`fs.rs` (一覧・ホーム・ドライブ・ディスク容量・ツリー表示用の配下の有無 `dirs_have_entries`)、`ops.rs` (作成・名前変更)、`open.rs` (外部アプリ・エディタ・ターミナルで開く)、`exec.rs` (選択したファイルへの外部コマンド実行)、`transfer.rs` (コピー・移動・削除。進捗通知と中断に対応)、`preview.rs` (プレビュー)、`info.rs` (詳細情報・配下の合計)、`config.rs` (キーマップ・アプリ設定ファイルの読み書き)、`history.rs` (ディレクトリの移動履歴の保存と読み込み)、`app.rs` (終了) に分け、`mod.rs` で再エクスポートする。
  - `src/main.rs`: エントリポイント。
  - `tests/`: テスト。直下の `*_test.rs` は結合テスト (`commands_test.rs` など)、`unit/` は単体テスト (`src/` と同じ構成で、ファイル名は `<ソースのファイル名>_test.rs`。`src/commands/transfer.rs` のテストは `unit/commands/transfer_test.rs`)。
  - `build.rs`: Tauri のビルド。アプリ独自のコマンドの一覧 (`COMMANDS`) から、権限 (`permissions/autogenerated/`。生成物) を作る。
  - `capabilities/default.json`: Tauri v2 の権限設定。
- `FILETREE.md`: 目標とするファイル構成 (`components/`、`features/` など、まだ存在しないものを含む)。
- `TODO.md`: フェーズごとのロードマップ。
- `KEYBINDINGS.md`: キーバインド仕様。
- `README.md` / `INSTALL.md` / `SETUP.md`: 利用者・開発者向けの文書。
- `INTEGRATION_TESTS.md`: 結合試験項目書 (実際に起動したアプリケーションでの, 画面操作単位の試験項目)。キーバインドや操作を変更したら, 該当する項目も見直す。
- `.github/workflows/release.yml`: `v*` タグの push で、3 OS 向けにビルドして GitHub Releases にドラフトを作る。
- `.github/workflows/debug-build.yml`: 手動実行で、選んだ OS 向けにデバッグ版 (`tauri build --debug`) をビルドし、Artifacts に置く (14 日で消える)。
- `dist/`、`coverage/`、`docs/`、`node_modules/`、`src-tauri/target/` は生成物。編集しない。

## コードの構成規約

### 共通

- フロントエンドとバックエンドは、Tauri の IPC (`invoke` とコマンド) だけで結ぶ。コマンドの名前・引数・戻り値を変えるときは、`src-tauri/src/commands/` 配下、`src-tauri/src/lib.rs` の `specta_builder` (`collect_commands!`)、`npm run bindings:generate` で作り直した `src/bindings.ts`、フロントエンドの呼び出し (`src/services/tauriApi.ts`)、両方のテストを、まとめて直す。
- Rust の構造体を IPC で返すときは、`serde::Serialize` と `specta::Type` を派生する。フロントエンドの型 (`FileEntry` など) は、手で書かず、`src/bindings.ts` (tauri-specta が Rust の型から作る。手で編集しない) から取り込む。シリアライズとデシリアライズで形が違う型 (`#[serde(default)]` など) は `_Serialize` / `_Deserialize` に分かれるので、受け取る型は `_Serialize` を使う。`src/bindings.ts` がコマンドと合っていないと, `cargo test` (`test_specta_builder_bindings_up_to_date`) が失敗する。
- 新しく IPC コマンドを追加したら、`#[tauri::command]` の後に `#[specta::specta]` を付け、`lib.rs` の `specta_builder` の `collect_commands!` に、サブモジュール込みのパス (`commands::ops::copy_item` など) で登録して、`npm run bindings:generate` を実行する。アプリ独自のコマンドは、許可したものだけを呼べるので、`build.rs` の `COMMANDS` にコマンド名を足し、`capabilities/default.json` に `allow-<コマンド名 (`_` を `-` にしたもの)>` を足す (漏れると `cargo test` の `test_capabilities_allow_every_command` が失敗する)。ディスクや外部プロセスを使うコマンドは、`#[tauri::command(async)]` にして、メインスレッドで実行しない。ファイルシステムやシェルなどのプラグインを使う場合は、`capabilities/default.json` の権限も追加する。
- コマンド (`M-x` / `:`)・新規作成・名前変更・削除確認・ドライブ選択は, ダイアログではなく `components/Minibuffer.tsx` (画面下部の入力領域) で表示する。進捗表示 (`TaskProgressModal`) や操作ログ・コマンド一覧 (`OperationLogDialog`, `HelpDialog`) のように, 文字入力を伴わないものは `components/Modal.tsx` (中央のダイアログ) のままでよい。ブックマーク一覧は, ダイアログでもミニバッファでもなく, `DualPaneContainer` の `overrides` でペインの表示そのものを差し替える (`BookmarkPane`)。
ドキュメントコメントは日本語で書く。文末は「.」を使う既存の書き方に合わせる (`/// ... します.`、`* @param` など)。
- コメントに、`// ---` や `// ===` のような、装飾の記号を入れない。

### バックエンド (Rust)

- 公開する関数・構造体には、`///` のドキュメントコメントを付ける。引数がある場合は `# Arguments`、戻り値がある場合は `# Returns`、パニックしうる場合は `# Panics` の節を書く。
- IPC コマンドは、`Result<T, String>` を返す。エラーは、呼び出し側 (フロントエンド) で表示できる文字列にする。
- ロジックは、Tauri のランタイムに依存しない関数として書き、`cargo test` で検証できるようにする。`tauri::Builder` の起動部分 (`run`) のように、テストできない部分だけを `#[cfg(not(tarpaulin_include))]` でカバレッジから除外する。
- `unwrap()` / `expect()` は、実行時のコード (`src`) では避け、エラーを `Result` で返す。テストでは使ってよい。
- 依存クレートは、`src-tauri/Cargo.toml` に追加する。テストだけで使うものは `[dev-dependencies]` に置く。

### フロントエンド (TypeScript / React)

- 関数コンポーネントとフックで書く。型は `any` を避け、明示する。コンポーネントの戻り値の型は `ReactElement`。
- 公開する型・関数・コンポーネントには、TSDoc (`/** ... */`) を付ける (typedoc で出力する)。
- Tauri の API は `@tauri-apps/api` から取り込む。バックエンドの呼び出しは、`src/bindings.ts` の `commands` (中で `invoke` を呼ぶ) を, `src/services/tauriApi.ts` から通す。
- ログは `console.*` ではなく `loglevel` (`log.debug` / `log.warn` / `log.error`) を使う。
- ログのレベル: デバッグ版 (`npm run tauri:dev`、`debug_assertions`) はデバッグ以上、リリース版は情報 (最低限)、警告、エラーを出す (Rust は `logging.rs` の `default_level`、フロントエンドは `App.tsx` の `log.setLevel`)。判定は、ログの初期化の中でする (呼ぶ側では、判定しない)。Rust は `log::debug!` / `info!` / `warn!` / `error!` を使う。フロントエンドのログは、`log_frontend_message` で、バックエンドのログにも転送する。
- ログは、標準エラー出力と、ログファイル (`<データディレクトリ>/rsfiler/logs/rsfiler.log`。5 MB で世代送り、3 世代) に出す。環境変数 `RUST_LOG` で、レベルを上書きできる。パスワードなどの秘密は書かない。
- キーボード操作を優先する。キーバインドを足すときは、`KEYBINDINGS.md` の既存の割り当てと衝突しないことを確認する。
- `FILETREE.md` の構成 (`components/`、`features/<機能>/{components,hooks,types.ts}`) に沿って、ファイルを分ける。コードが `App.tsx` に集中してきたら、この構成へ切り出す。

## テストの規約

### Rust

- テストのソースは、すべて `src-tauri/tests/` に置く (`src/` には置かない)。
  - 単体テストは、`src-tauri/tests/unit/` に、`src/` と同じ構成で、`<ソースのファイル名>_test.rs` の名前で置く。非公開の関数も検証できるよう、対象のソースの末尾で `#[cfg(test)] #[path = "../../tests/unit/commands/transfer_test.rs"] mod tests;` のように子モジュールとして組み込み、テストの中では `use super::*;` を使う。テスト用の偽物 (`FakeClipboard` など) も、テストのファイルに置く。
  - 結合テストは、`src-tauri/tests/` の直下に `*_test.rs` で置き、公開 API (`rsfiler::commands::*`) だけを使う。`unit/` の下は, cargo が結合テストとして別に組まない (`main.rs` を置かない)。
- テスト関数名は `test_<対象の関数名>_<内容>` とする (`test_read_directory_integration`)。
- ファイルシステムを使うテストは、`tempfile` の一時ディレクトリを使い、実際のホームディレクトリなどを変更・削除しない。
- 同じ挙動を検証する、重複したテストは作らない。

### フロントエンド (vitest)

- テストは `tests/` に、`src/` と同じ構成で置く。ファイル名は、対象のソースのファイル名に `.test` を付ける (`src/App.tsx` → `tests/App.test.tsx`)。1 つのソースのテストは 1 つのファイルにまとめる。
- テストから `src/` のモジュールは、`@/` で取り込む (`import App from "@/App"`。`vite.config.ts` の `resolve.alias` と `tsconfig.json` の `paths`)。
- `@tauri-apps/api/core` の `invoke` は、`vi.mock` でモックする。テストから、実際の Tauri のバックエンドやファイルシステムへ接続しない。
- `describe` で対象 (コンポーネント・フック・関数) をまとめ、`it` の説明は、日本語で「正常系: ...」「異常系: ...」のように、何を検証するか分かるようにする。
- 各テストの前に `vi.clearAllMocks()` を呼び、テスト間でモックの状態を持ち越さない。
- ユーザー操作は、`@testing-library/user-event` で再現する。

## 開発ルール

- コードの修正後は必ず `npm run build` `npm run check` を実行し、エラーが出なくなるまで修正を繰り返すこと。
  - `npm run check` は、整形チェック・eslint・clippy・vitest・cargo test・`cargo fmt --check` を含む。整形で失敗したら、`npm run format` で直してから、もう一度実行する。
  - Rust だけ変更した場合でも、フロントエンドの型と IPC の整合を確認するため、`npm run check` は省略しない。
  - **例外**: 変更が Markdown ファイル (`*.md`) のみの場合は、上記のコマンドを実行しない。
- 機能追加・修正には、テストを追加する (フロントエンドは vitest、バックエンドは cargo test)。カバレッジは下げない (`npm run coverage` で確認する)。フロントエンドもバックエンドも 100% を保つ (フロントエンドは `vite.config.ts` の `thresholds`、バックエンドは `coverage:be` の `--fail-under 100`。下回ると失敗する)。バックエンドは、ジェネリックな関数の行を正しく数えるため、tarpaulin の LLVM の計測 (`--engine llvm`) を使う。OS ごとに異なる処理は、`cfg!` の分岐ではなく、`#[cfg]` で関数を分ける (他の OS の処理を数えないため)。到達できないコードは削除する。カバレッジからの除外 (`tarpaulin_include`、vitest の `coverage.exclude`) は、エントリポイントや、テストできない起動処理に限り、理由をコメントで添えて使う。
- キーバインドや操作を変更したら、`KEYBINDINGS.md` と `README.md` も更新する。フェーズの進捗が変わったら `TODO.md`、ファイル構成が変わったら `FILETREE.md` も更新する。既存の画面操作に影響する変更 (キーの割り当て・確認手順・表示内容など) は、`INTEGRATION_TESTS.md` の該当項目も見直す。
- `package.json` の `version`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json` のバージョンは、勝手に変更しない (リリースの操作は、ユーザーが行う)。
- `package-lock.json` と `Cargo.lock` は、依存を変更したときだけ更新する。

### 完了条件・タスク完了時の動作

- 修正や機能追加が完了し、ビルドやテストが全て成功したら、以下の手順を実施してタスクを終了すること：
  1. `git diff --stat` を実行して必要に応じて主要ファイルの差分を確認すること。
  2. 修正内容のサマリー（変更点と理由の簡潔なまとめ）をユーザーに報告する。
- ユーザーに依頼されない限り、`git commit` / `git push` は行わない。

## コミットガイドライン

- コミットメッセージは英語で記述
- **件名は、Conventional Commits の形式で書く**: `type(scope): description`。scope (括弧を含む) は、省略できる。description は、英語で、命令形 (例: `feat(tree): Show files in the tree view`)。
  - type は、次のどれか。
    - `feat`: 機能の追加
    - `fix`: バグの修正
    - `docs`: 文書とコメントだけの変更 (`*.md`、TSDoc、Rust の `///` コメント)
    - `style`: 整形、規約の適用 (動作を変えない)
    - `refactor`: 動作を変えない、書き換え
    - `test`: テストだけの変更
    - `build`: ビルドと、開発環境 (`package.json`、`vite.config.ts`、`tsconfig*.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`) の変更
    - `ci`: CI (`.github/`) の変更
    - `chore`: そのほかの雑務 (最初のコミット、`.gitignore`、依存パッケージの更新 (`package-lock.json`) など)
  - scope は、変更の場所: 機能 (`src/features/` のディレクトリ名: `explorer` / `operations` / `preview` / `search` / `keybindings` / `settings` / `bookmarks` / `tree`)、`backend` (`src-tauri/` だけの変更)、`deps` (依存パッケージの更新)。複数の機能にまたがるときは、省略する。
  - 互換性を壊す変更は、type (または scope) の直後に、感嘆符を付ける (Conventional Commits の仕様のとおり)。
  - 複数の type にまたがるときは、変更の中心になる type にする。
- 件名のあとに空行を 1 行入れて、本文を書く。本文はダッシュ/ハイフンで始まる箇条書き (例: `- Fix bug in parser`)。箇条書きの各行の間には、空行を入れない
- コミットメッセージに `Co-Authored-By` または Claude 帰属行を含めない
- **rebase したあとの push は、`git push --force-with-lease --force-if-includes origin <ブランチ名>` で行う** (`--force` は使わない。リモートに、手元に取り込んでいないコミットがあれば、push は失敗する)。ユーザーに依頼されたときだけ、push する。
